# 架构设计

状态：目标架构。当前已实现核心、初版存储、插件界面及部分 AI 接入；实际交付与未完成项见 [实现状态](status.md)。schemaVersion 1 仍处于开发预览阶段。

## 分层

```text
Obsidian 插件界面：连续阅读 / Notebook / 就地问题 / 草稿预览
                         │
文档核心：节点、问题、覆盖关系、阅读路径、版本与事务
            ┌────────────┴────────────┐
Markdown 与伴随元数据              上下文构建与任务执行
                                       │
                          模型 / Agent / 客户端交接适配器
```

采用 TypeScript；复杂交互视图使用 React，编辑区采用 CodeMirror 6 的 Markdown 能力，打包对接 Obsidian。核心模块不得依赖 Obsidian、React 或某家模型 SDK。使用 pnpm workspace 管理插件与核心，避免首版拆成过多服务。

初始代码目录计划为：

```text
apps/obsidian/       插件入口、视图、Vault 读写和设置
packages/core/      领域对象、操作、状态投影和上下文计划
packages/ai/        后端接口、直接模型调用和测试后端
packages/bridge/    后续加入的桌面 Agent 与客户端交接
fixtures/           Markdown 样例、编辑和恢复案例
docs/               产品规则、设计和验收标准
```

基础编辑无需后台服务。需要运行 Codex 或 Claude Agent SDK 时，再由桌面适配器管理本地子进程；不为首版增加云端账户系统或常驻远程服务。

## 当前内容与历史记录

Markdown 是当前正文及主线顺序的权威来源。伴随元数据保存节点身份、问题、关系、阅读位置和结构版本；其中的内容哈希只用于校验，不是另一份可独立编辑的正文。首版 ReadingPath 的主路线顺序是 Markdown 的派生投影，不能用旧路线反向恢复正文；未来的命名替代路线才会独立保存其排列。

历史记录追加保存变更事件及必要的旧内容版本，用于恢复、撤销和上下文构建。历史不能反向悄悄覆盖当前 Markdown。有限上下文窗口中的模型消息与持久历史记录分开管理。

上述持久事件历史是后续目标；当前采用内存撤销令牌及磁盘写入意图记录。已收取草稿另存于 `article.explainweave.drafts.json`，Cowork 任务包保存在 `.explainweave-handoffs/`，二者都不能作为当前正文来源。

M0 先验证同目录伴随文件 `article.explainweave.json` 的方案：文件含 schemaVersion、documentId、正文校验值和元数据。节点身份在受管理文章中使用隐藏的 Markdown 注释标记，普通阅读不显示；首次启用须提供转换预览，干净导出时可移除标记。对不愿添加标记的文章先提供旁注模式，依赖引用文字和邻接上下文定位；出现歧义时保留问题并提示重新定位，不假装实现可靠双向编辑。

历史文件的位置、大小上限和同步策略在 M0 一并验证。伴随文件必须能随文章备份和导出，不能只保存在插件安装目录。隐藏目录能否被具体同步工具同步，需要实际验证，不能默认支持。

## 主要对象

| 对象 | 用途 |
| --- | --- |
| Document / Node / NodeRevision | 文章、稳定的解释单元身份、不可变内容版本 |
| Question / QuestionRevision | 问题身份及文字版本、原始选区、所属节点和可选父问题 |
| ExplanationLink | 回答版本与具体文字范围、被覆盖的问题版本、覆盖程度和判断来源 |
| ReadingPath / Cursor | 阅读顺序、当前位置和支线返回位置 |
| Draft / Task | AI 草稿、目标位置、生成依据、状态和采用条件 |
| Change / Checkpoint | 可恢复的变更操作与状态快照 |

引用同时记录版本与文字锚点。可重复使用的内容和在阅读路径中的具体出现位置分开建模；当前阅读覆盖按路径中的出现位置判断。Task 保留用户的提问或补写要求、所用上下文版本及结果关联；修改要求并重新生成时创建新的尝试，旧草稿仍可追溯。

## 编辑、并发与恢复

插件发起的修改通过核心操作入口进入：插入、移动、拆分、合并、删除、提出问题、采用草稿和关联解释。操作同时描述正文与关系变更，并携带预期版本。原生 Markdown 编辑器或外部程序的修改由文件事件触发对账：先读取实际正文，再重建可确定的节点映射和主路线；无法确定时保留外部正文，暂停受影响的自动写入，等待重新定位。

采用 AI 草稿前校验目标位置和依赖版本。若生成期间正文已改变，保留草稿并提供比较或重新生成，不能按过期偏移量覆盖内容。重复完成通知通过任务 ID 去重；取消后的迟到结果不能自动采用。

Markdown 与伴随文件不能假定具有跨文件原子写入。使用带校验值的写入意图记录、临时文件、提交标记及启动恢复；检测外部修改和同步冲突后暂停相应自动写入，并保留冲突版本。首版采用单活动写入者，不宣称支持 CRDT 或多设备同时编辑。

撤销针对一次操作及其关系变更，不能直接把整份文章恢复到旧快照而抹掉后续手写内容。无法安全反向应用时显示冲突并保留两版。外部编辑后仅更新受影响区域的定位与状态。

修改问题文字、回答或其前提后，关联进入待检查；移动回答后重算路径前缀覆盖。覆盖依据同时绑定问题版本与回答版本，不能把旧问题的答案自动视为新问题的充分解释。结构有效性可以自动检查，语义上的充分解释仍是 AI 判断，需要展示依据和可纠正入口。

## 上下文与缓存

文档的逻辑排列与模型收到消息的物理排列分离。对于由应用控制请求的直接模型后端，在单个有界任务会话内保持已发送历史稳定，追加新问题、修改后的节点版本与明确的有效版本说明。应用先解析当前状态，不要求模型从无限事件日志中还原文章。

局部补写优先包含任务、当前位置、相关原文、问题、必要前提与全文结构摘要。摘要不能代替做判断所需的原文；缺少内容时读取相应节点。全文连贯性检查作为独立任务，避免每次局部编辑都携带整篇文章。

本地持久事件记录可持续追加，但模型会话必须设置预算与检查点。超过阈值后，生成新的当前状态快照并开启新上下文，记录这次重建。切换后端时传递中立的文档状态与必要历史，不能直接复用另一家的私有会话。

缓存命中受前缀、有效期、模型与服务端策略影响，不承诺固定节省比例。Codex 等 Agent 自己可能压缩和改写内部上下文；适配器要声明是应用控制请求，还是运行时控制上下文。对请求记录输入、缓存读取/写入、输出、延迟和总任务开销，缺失指标显示未知而不是零。

## AI 与文档操作边界

AI 返回有来源和版本的建议操作，由核心校验再形成草稿。首次版本中，Agent 通过范围明确的读文档、读节点、列出问题、提交草稿工具工作，不能绕过核心直接改写正式文章。工具结果和导入文章属于内容，不得提升为应用指令。

凭据不写入 Markdown、伴随文件或会被同步的日志。优先使用运行环境的凭据设施；未确定持久化方式前允许仅会话保存。发给第三方模型的内容范围可检查。客户端交接只导出选定任务包，回收文件按不可信输入进行版本、路径和格式校验。
