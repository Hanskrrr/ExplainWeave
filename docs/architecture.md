# 架构设计

状态：0.2 开发预览。本文区分当前实现与后续目标；真实环境验证边界见 [实现状态](status.md)。数据格式仍使用 schemaVersion 1，尚未冻结为稳定发布格式。

## 分层

```text
Obsidian：连续阅读 / Notebook / 文章与问题讨论 / 候选正文
                         │
控制器：文档操作、讨论历史、后续安排、生成与采用
            ┌────────────┴────────────┐
文档核心与存储                    上下文日志与 AI 适配器
节点、问题、引用、版本             直接模型 / 客户端交接
```

采用 TypeScript、React 和 CodeMirror 6，使用 pnpm workspace。文档核心不依赖 Obsidian、React 或模型 SDK。基础编辑无需后台服务，不为首版增加云端账户系统或常驻远程服务。

```text
apps/obsidian/       插件、视图、控制器、Vault 读写和设置
packages/core/      领域对象、不可变操作和覆盖投影
packages/ai/        上下文日志、请求接口、直接模型调用和测试后端
packages/bridge/    Cowork 任务包、深链接和返回校验
fixtures/           Markdown 样例、编辑和恢复案例
docs/               产品规则、设计和验收标准
```

Codex 与 Claude Agent SDK 尚未接入。未来需要可编程 Agent 时，再由适配器管理其运行时；客户端交接与直接模型调用保留各自能力边界。

## 当前内容与保存边界

Markdown 是当前正文和主线顺序的权威来源。`article.explainweave.json` 保存节点身份、问题、解释关联、阅读位置与结构版本；内容哈希用于校验，不是另一份可独立编辑的正文。当前阅读路线从 Markdown 顺序派生，不能用旧元数据排列反向覆盖正文。

受管理文章使用隐藏 Markdown 注释作为稳定节点标记，首次启用前展示转换预览；干净导出可移除标记。遇到重复、缺失或不能安全解析的标记时，保留实际正文并提示恢复，不猜测身份后强行写入。

| 文件或状态 | 当前用途与权威范围 |
| --- | --- |
| `article.md` | 当前正文及节点顺序 |
| `article.explainweave.json` | 问题、引用关系、节点版本和阅读位置 |
| `article.explainweave.pending.json` | 正文与元数据未完成提交的意图及恢复依据 |
| `article.explainweave.sessions.json` | 文章 / 问题讨论、原始模型消息、后续安排和上下文日志 |
| `article.explainweave.drafts.json` | 候选草稿及生成依据，不是当前正文 |
| `.explainweave-handoffs/` | Cowork 任务包与交接依据，不是当前正文 |
| 内存撤销令牌 | 当前打开会话中的安全反向操作；重启不保留 |

`.md` 和解释元数据属于同一可恢复的正文提交。讨论、草稿和交接文件独立保存、各自检查已知外部冲突；没有跨这些全部文件的原子事务。备份和迁移必须保留相关伴随文件；具体同步工具是否同步隐藏目录仍需实测。

## 主要对象

| 对象 | 用途 |
| --- | --- |
| Document / Node | 文章、稳定节点身份、当前不可变内容版本 |
| Question | 问题身份与版本、原始引用、所属节点、可选父问题 |
| ExplanationLink | 问题和回答版本、具体引用、覆盖程度、前提依赖与判断来源 |
| Reading / Cursor | 当前节点、活动问题和返回主线的位置 |
| Discussion / ChatTurn | 文章或某个问题的可读问答记录，包括生成、取消与错误状态 |
| Discussion.transcript | 实际模型消息序列，保留结构化生成 JSON 和已保存的部分输出 |
| QuestionPlan | 某问题安排在哪个后续节点解释及其问题版本 |
| Draft | 候选正文、解释建议、目标位置与采用依据 |
| ContextJournal | 按序追加的节点版本、删除记录和当前排列 |

子问题首次开始模型讨论时从父支线原始消息建立分支，随后保存自己的序列；父支线后来变化不追改已发送历史。界面中的 Markdown 记录与模型原始消息分开保存，避免把整理后的正文误当成模型此前实际收到或返回的文本。中断恢复把生成状态改为已取消，保留已保存片段，不重写原始消息内容。

后续安排仅记录写作意图。聊天回答、计划和未采用草稿均不参与正文覆盖；只有指向有效正文、位于当前阅读路线前缀内的解释关联参与计算。修改问题、父问题、回答或已记录前提，或改变相关路线顺序，会重算覆盖或标为待检查。

## 编辑、采用与恢复

插件修改通过核心的不可变操作入口进入：节点增删改移、拆分合并、问题、阅读位置和解释关联。原生 Markdown 编辑器或外部程序的修改触发对账，先读取实际正文，再重建可确定的节点映射；无法确定时保留正文并暂停受影响的自动写入。

**整理成正文节点** 与 **用 AI 写节点** 先生成候选草稿。返回的解释建议必须绑定当前任务的问题，并给出候选正文中唯一可定位的引用；目标、版本或结构无效时拒绝采用。模型对“完整解释”或“部分解释”的判断不是语义证明，用户可以查看依据、移除关联并修正。

点击 **采用为后续解释** 时，在临时不可变状态中完成正文插入和该草稿的全部解释关联，再一次提交最终 Markdown 与元数据。撤销令牌覆盖这一组变化，**撤销** 一起撤回正文和关联；不能只撤回最后一条关系或恢复整份旧文章覆盖后续手写内容。导航不使内容撤销失效，后来不同的内容修改或外部变化仍须通过安全检查。

正文提交先记录带完整校验的写入意图，再更新 Markdown 与元数据，启动时可恢复未完成提交。该机制提供恢复能力，不是文件系统跨文件原子写入；FileIO 也不能保证跨进程 compare-and-swap。当前要求单活动写入者，检测到已知冲突保留原文件并拒写，不支持多设备同时写入。

正文采用成功后，若讨论或草稿旁文件保存失败，正文提交不会因此自动回滚。错误处理必须区分已提交正文和待保存旁状态，避免重试时再次插入。旁文件读取损坏、未知格式、不同文章或超限数据时拒绝覆盖；保存前比较预期原文，外部修改后须重新加载再处理。

撤销目前只保留在打开的笔记会话内。持久化完整编辑事件和跨重启撤销是后续目标；现有上下文日志不能作为用户正文或完整撤销历史的替代来源。

## 上下文与缓存

逻辑文档排列、持久讨论记录和发给模型的线性消息序列是不同对象。当前模型请求包含文章上下文、问题和相关讨论的完整历史，不做静默截断或用摘要替代原文。文档中间编辑后，ContextJournal 追加节点新版本、删除记录（tombstone）和新的节点排列；模型根据明确的当前有效状态理解文章顺序，不通过重排旧消息表达改稿。

每个讨论保存实际原始消息序列。后续请求保留此前已发送的消息，再追加文档增量、新要求和模型回答；结构化生成的原始 JSON 也保留在序列中。同一讨论不会每轮把新文档日志插到旧聊天记录前方。父支线首次被继承后形成独立分支，后续不因父讨论变化改写子讨论的旧消息。

当前不自动 checkpoint。底层提供 checkpoint API 供未来显式上下文重建使用，但只清空文档日志不会缩短已经包含旧日志的讨论消息。要控制长期增长，仍需实现可见的新会话、可审查的总结压缩及完整上下文重建；这些操作会建立新前缀，必须与原历史分开说明。

完整历史和增量有长度与成本边界：本地文件、字段和消息数量有限，服务上下文窗口也有限。超限报错并保留已有数据，不截掉早期历史后冒充完整会话，亦不保证长会话无限继续。流式内容尚未落盘时突然退出，仍可能损失最近片段。

消息前缀稳定只为缓存复用创造条件，不能保证后缀 KV 可以跨重排复用，也不能保证服务端实际命中。缓存还受模型、工具 / 系统配置、有效期和服务策略影响；本版尚未测得缓存收益。当前显示后端提供的用量字段，缺失值不当作零；完整成本比较和延迟测量仍待真实服务验收。未来 Agent 运行时可能自行压缩消息，其上下文控制权必须单独声明。

## AI 与文档操作边界

AI 提交候选正文和引用建议，控制器校验后经文档核心采用；不能直接绕过版本检查写入正式文章。当前没有向 Codex 或 Claude Agent SDK 暴露一套已实现的文档工具。文章、工具返回内容和导入文件均作为数据处理，不提升为应用指令。

API 密钥仅保存在当前会话，不写入 Markdown、伴随文件或同步日志。模型请求包含文章与讨论历史；后端和模型可由用户选择。Cowork 交接导出独立任务包，回收文件作为不可信输入进行任务身份、版本、字段及路径检查，只有通过校验才成为候选草稿；打开客户端链接不等于任务已发送或完成。
